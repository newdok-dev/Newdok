# Spec: 구독 관리 TCA 전환

> Status: approved — 2026-11-14, 사용자가 전환안을 검토한 뒤 “브랜치 파서 ㄱㄱ”로 구현을 승인했다.

> 구조 정리 승인 — 같은 날 “수정 ㄱㄱㄱㄱ”로 화면 이름 통일, TCA 의존성 주입, Store 소유 위치 정리를 승인했다.

## 배경 / 문제

사용자는 화면마다 별도의 상태 처리 규칙을 만드는 대신 TCA로 코드를 일관되게 작성하는 방향을 제시했다. 첫 전환 대상은 재현 가능한 오류가 있고 Builder 경계가 분리된 구독 관리다.

현재 View가 구독 변경과 후속 목록 조회를 조율하고, ViewModel은 두 탭의 갱신을 하나의 플래그로 막는다. 실제 ViewModel에 임시 재현 테스트를 적용한 결과 기존 11개 테스트는 통과했고 다음 3개 수용 조건은 실패했다.

1. 새로고침 실패 후 재시도가 최신 목록을 다시 조회한다.
2. 한 탭의 조회 중 다른 탭을 선택해도 새 탭 조회가 유실되지 않는다.
3. 구독 중지 전 시작된 조회가 늦게 끝나도 중지 이후 화면을 이전 상태로 남기지 않는다.

진단 기록: `/private/tmp/newdok-subscribe-architecture-audit.log`, 임시 재현 코드: `/private/tmp/SubscribeArchitectureAuditTests.swift`. 이 파일들은 로컬 진단 자료이며 구현 시 회귀 테스트를 저장소 안에 작성한다.

## 목표 (Goals)

- 구독 화면의 상태 변경, 비동기 작업, 취소, 재시도를 TCA의 한 가지 방식으로 관리한다.
- 재현된 3개 오류를 해결하고 중지·재개·탭 변경·인증 변경의 상태 전환을 검증한다.
- 다음 화면에서 재사용할 수 있는 코드 작성 규칙을 구독 기능의 실제 구현으로 확정한다.
- 화면 디자인, 게스트 진입, 탐색 콜백, 접근성과 기존 분석 이벤트 의미를 보존한다.

## 비목표 (Non-goals)

- 이번 변경에서 다른 Feature나 App 라우팅 전체를 TCA로 전환하지 않는다.
- 공용 BaseReducer, 자체 Store/Effect, 자동 코드 생성기를 추가하지 않는다.
- 서버 API·인증 정책·배포 설정을 바꾸지 않는다.

## 유저 스토리

- 사용자는 구독을 중지하거나 재개하면 두 목록에서 일관된 상태를 본다.
- 사용자는 탭을 바꾸거나 재시도를 눌렀을 때 요청이 조용히 생략되지 않는다.
- 개발자는 사용자 행동부터 응답 반영까지 같은 구조로 읽고 테스트한다.

## 수용 조건 (Acceptance Criteria)

- [x] 구독 화면의 업무 상태는 TCA State가 단독 소유하며 기존 ViewModel의 중복 상태를 남기지 않는다.
- [x] 초기 로드 후 발생한 조회 실패도 재시도로 복구된다. 변경 요청 실패와 조회 실패의 재시도 대상을 구분한다.
- [x] 한 탭 조회 중 다른 탭으로 전환해도 선택한 탭의 최신 결과를 표시한다.
- [x] 중지·재개 성공 후 두 목록이 일관되게 갱신되고, 변경 이전 응답이 최신 목록을 덮어쓰지 않는다.
- [x] 중지·재개 요청이 성공한 뒤 목록 조회만 실패하면 재시도는 조회만 수행한다.
- [x] 동일 구독의 중복 변경을 막고, 실패하면 다시 조작할 수 있다.
- [x] 화면 이탈·인증 변경 시 작업 수명을 정리하고 이전 사용자 결과·오류·성공 표시가 새 상태에 반영되지 않는다.
- [x] 취소는 사용자 오류로 표시하지 않는다. 변경 요청 취소를 서버 처리의 취소로 가정하지 않고 복귀 시 재조회한다.
- [x] 기존 게스트/빈 목록/정상 목록, 구독 확인 팝업, 성공 토스트, 접근성, 목록 분석 이벤트를 보존한다.
- [x] Swift Testing의 TestStore 테스트로 위 흐름을 검증한다. 실제 네트워크·임의 sleep·공유 전역 상태를 사용하지 않는다.
- [x] 자체 Feature·Testing·Tests·Example 타깃의 Swift 6/strict concurrency complete를 유지한다.
- [x] Tuist 프로젝트 생성, 구독 모듈 테스트, 전체 테스트, SubscribeExample 빌드와 `fastlane build`가 성공한다.

## 구조 정리 수용 조건

- [x] 화면 타입과 파일을 `SubscriptionsFeature`, `SubscriptionsView`, `SubscriptionRow`, `EmptySubscriptionsView`로 통일한다.
- [x] Reducer는 `@Dependency`로 의존성을 읽고, 기존 Domain UseCase와 Repository는 Builder에서 조립한다. 별도 DIContainer를 제거한다.
- [x] Builder의 진입 View가 Store 수명을 소유하며 화면 View는 전달받은 Store를 관찰한다. 계정 변경으로 탭 identity가 바뀌면 Store도 새로 생성한다. Example은 Store를 body 밖에서 생성한다.
- [x] 기존 11개 동작 테스트와 Example·앱 빌드가 이름 및 주입 방식 변경 이후에도 통과한다.

## 열린 질문

- 제품 동작에 대한 추가 질문은 없다. 구현 범위와 수용 조건은 이 초안을 기준으로 검토한다.
